> **一言でいうと:** コードを書く前にClaudeに「計画」を出させ、承認してから実装させる。これで的外れな誤実装が世に出るのを防ぐ。複数ファイルにまたがる／高リスクなタスクで使う。

# 目的

あらゆる実装タスクを3つの明確で重複しないフェーズに分割する。計画と実行の分離は Claude Code における最高レバレッジのパターン：「計画が良ければ、コードが良い」。

# 使用タイミング

- 複数ファイルにまたがる実装タスク全般
- チケット・イシュー・PRDから作業する場合
- 高リスクな変更（認証、決済、データ移行）
- 自信過剰な誤実装のコストが高い場合

# 使用しないタイミング

- 些細な1行修正
- 純粋な探索・読み取り専用タスク
- 使い捨てプロトタイプ

# 入力

- 受け入れ基準付きのチケット/イシュー説明
- ファイルスコープ（対象ファイル一覧）
- テストスイートの場所
- Jira/Linear チケット ID（任意）

# ワークフロー

## フェーズ1：計画（読み取り専用、ファイル変更なし）

```
チケット [ID] を読み込む。計画フェーズのみ開始する。
関連ファイルをすべて読む。変更が必要なファイルをすべて特定する。
各変更の根拠とともに番号付きプランを作成する。
ファイルは変更しないこと。承認を待つ。
```

**プランに含めること：**
- 変更するファイル（行番号付き）
- 各変更の根拠
- 変更しないものの明示的なリスト
- 推定テストコマンド

**ゲート**：フェーズ2に進む前に Human がレビューして承認する。

## フェーズ2：実装（承認済みプランのみ実行）

```
プラン承認済み。項目1からNを順番に実行する。
進める前に各ファイル変更がプランと一致することを確認する。
予期しないことに遭遇したら停止して報告する。
承認済みプランを超えた即興はしないこと。
```

**ルール：**
- プランの項目を順番に実行する
- 承認済みプランを超えたスコープクリープなし
- 予期しない状態に遭遇したら即座に停止
- 逸脱を報告する。自動修正しない

## フェーズ3：検証（テスト実行、受け入れ基準確認）

```
実装完了。検証を実行する：
1. 実行：[テストコマンド]
2. 各受け入れ基準を確認：[チケットのリスト]
   - 各基準について明示的に pass/fail を報告する
3. いずれかの基準が失敗した場合：停止する。失敗を報告する。指示を待つ。
   失敗を自動修正しないこと。
```

**ルール：**
- 各基準について明示的に pass/fail を報告する
- 検証失敗を自動修正しない
- 全基準が pass した後にのみチケットのステータスを更新する

## 検証失敗プロトコル

```
停止する。自動修正を試みないこと。
以下を報告する：
- どの基準が失敗したか
- なぜ失敗したか（根本原因）
- 新しいプラン項目としての修正案
Human の承認を待ってから修正を実装する。
```

# 成功基準

- 計画フェーズでファイル変更が発生しない
- 実装が承認済みプランと完全に一致する
- 検証が各基準について明示的な pass/fail を報告する
- サイレント失敗がない（全失敗が Human に報告される）

# 失敗パターン

- **プラン承認のスキップ**：Human レビューなしで計画から実装に進む
- **検証失敗の自動修正**：報告せずにサイレントにパッチする
- **実装中のプラン膨張**：承認済みプランにないスコープを追加する
- **受け入れ基準の欠落**：全基準を確認せずにテストを実行する
- **テスト不能な基準**：「正しく動作すること」は基準ではない

# ベストプラクティス

- 開始前に受け入れ基準を二値テスト可能なアサーションとして書く
- 監査証跡のためにプランを `docs/plan-[機能名].md` に保存する
- 読み取り専用フェーズを強制するために `/plan` モード（Shift+Tab）を使う
- マルチチケット追跡のために `docs/ticket-map.json` を管理する
- 各サイクル後に学んだことで CLAUDE.md を更新する

# アンチパターン

- 書面による受け入れ基準なしに PIV を実行する
- 実装中に Claude が「少し整理する」ことを許可する
- 検証失敗を些細なこととして扱う — 常に Human 承認でゲートする
- Human チェックポイントなしの PIV（目的を損なう）

# プロンプト例

```
チケット AUTH-42 を読み込む。PIV ループを開始する。

計画フェーズ：auth 関連のファイルをすべて読む。JWT リフレッシュトークンの
ローテーションを実装するために変更が必要なすべてのファイルを特定する。
行番号付きの変更リストを作成する。ファイルを変更しないこと。
プランを提示して承認を待つ。
```

```
プラン承認済み。実装フェーズを開始する。
プランの項目1〜5を順番に実行する。
プランにないものに遭遇した場合は停止する。
```

```
実装完了。検証フェーズを開始する。
実行：npm test -- --grep "auth"
その後、各基準を確認する：
1. リフレッシュトークンが使用時にローテーションされる（pass/fail）
2. 期限切れリフレッシュトークンが401を返す（pass/fail）
3. ローテーション後に古いトークンが無効化される（pass/fail）
いずれかが失敗した場合：停止して報告する。自動修正しない。
```

# コマンド例

```bash
# プランのみモードに入る
claude --permission-mode plan

# またはセッション中にスラッシュコマンドで
/plan

# 承認後に実装モードに切り替える
/implement
```
